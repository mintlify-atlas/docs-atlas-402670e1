Installing DBImport involves unpacking the distribution tarball, installing Python dependencies, editing the central configuration file, generating an RSA keypair for credential encryption, and initialising the MySQL configuration schema. This page walks through every step in order. For a list of prerequisites — Python version, Kerberos, MySQL version, and Hive transport mode — see the [Requirements](/requirements) page first.

---

<Steps>

  <Step title="Download and Unpack the Tarball">

    Download the latest release from the [DBImport GitHub Releases page](https://github.com/BerryOsterlund/DBImport/releases). Create the installation directory and extract the archive.

    ```bash
    mkdir /usr/local/dbimport
    cd /usr/local/dbimport
    tar -xf dbimport-VERSION.tar
    ```

    All subsequent commands in this guide are run from `/usr/local/dbimport` unless noted otherwise.

  </Step>

  <Step title="Install Python Dependencies">

    DBImport is verified with Python 3.6 and Python 3.8. Choose the requirements file that matches your Python version. Using a virtual environment is strongly recommended.

    <Tabs>
      <Tab title="Python 3.8 (Spark 3)">
        Python 3.8 requires Spark 3. Install the pinned dependencies with:

        ```bash
        pip3.8 install -r bin/requirements_python38.txt
        ```
      </Tab>
      <Tab title="Python 3.6 (Spark 2 or 3)">
        Python 3.6 works with both Spark 2 and Spark 3. Install the pinned dependencies with:

        ```bash
        pip3.6 install -r bin/requirements_python36.txt
        ```
      </Tab>
    </Tabs>

    If you plan to use Spark, set the `PYSPARK_PYTHON` environment variable to the same Python interpreter that DBImport uses. Both the local DBImport code and the Spark executor code must run with the same Python version.

    ```bash
    export PYSPARK_PYTHON=python3.8
    ```

  </Step>

  <Step title="Configure dbimport.cfg">

    The file `conf/dbimport.cfg` is the central configuration for DBImport. Copy the distribution template and edit it before running any DBImport commands.

    ```bash
    cp conf/dbimport.cfg.dist conf/dbimport.cfg
    ```

    The following sections and keys must be configured for a basic installation.

    ### [Database] — Configuration database connection

    ```ini
    [Database]
    mysql_hostname = db.example.internal
    mysql_port     = 3306
    mysql_database = DBImport
    mysql_username = dbimport
    mysql_password = dbimport
    ```

    For AWS deployments, set `aws_secret_name` to the ARN of an AWS Secrets Manager secret instead of providing plain-text credentials.

    ### [Kerberos] — Keytab and principal

    ```ini
    [Kerberos]
    keytab    = /etc/security/keytabs/dbimport.keytab
    principal = dbimport@EXAMPLE.COM
    ```

    DBImport renews this ticket automatically at the start of every import or export run.

    ### [Metastore] — Hive Metastore database

    ```ini
    [Metastore]
    metastore_type            = hive_direct
    hive_metastore_alchemy_conn = mysql+pymysql://USER:PASSWORD@metastore-db.example.internal:3306/hive_metastore
    ```

    For AWS environments using Glue, set `metastore_type = glue_catalog` and leave `hive_metastore_alchemy_conn` empty.

    ### [Hive] — HiveServer2 binary endpoint

    ```ini
    [Hive]
    servers               = hiveserver1.example.internal:10000,hiveserver2.example.internal:10000
    kerberos_service_name = hive
    kerberos_realm        = EXAMPLE.COM
    use_ssl               = false
    ```

    <Warning>
      The Hive server must be configured for **binary transport mode**. HTTP transport is not supported by DBImport.
    </Warning>

    ### [Airflow] — Airflow metadata database

    ```ini
    [Airflow]
    airflow_mode        = default
    airflow_alchemy_conn = mysql+pymysql://USER:PASSWORD@airflow-db.example.internal:3306/airflow
    ```

    This section is only required if you use the Airflow DAG generation feature. Set `airflow_mode = aws_mwaa` when running on AWS Managed Workflows for Apache Airflow.

    ### [REST_statistics] — Disable external statistics posting

    If you do not have a REST statistics endpoint, disable outbound posting to avoid connection errors on every import.

    ```ini
    [REST_statistics]
    post_column_data = false
    post_table_data  = false
    ```

    ### [Credentials] — SSL keypair paths

    ```ini
    [Credentials]
    private_key = conf/dbimport_private_key.pem
    public_key  = conf/dbimport_public_key.pem
    ```

    Relative paths are resolved from the `DBIMPORT_HOME` directory. Generate the keypair in the next step.

  </Step>

  <Step title="Generate the SSL Keypair">

    DBImport encrypts all JDBC usernames and passwords with an RSA public/private keypair before writing them to the configuration database. Generate the keypair with the following commands.

    ```bash
    openssl genrsa -out conf/dbimport_private_key.pem 8192
    openssl rsa -in conf/dbimport_private_key.pem \
                -out conf/dbimport_public_key.pem \
                -outform PEM -pubout
    ```

    Once generated, restrict file permissions so that only the DBImport service account can read the private key.

    ```bash
    chmod 600 conf/dbimport_private_key.pem
    chmod 644 conf/dbimport_public_key.pem
    ```

    <Warning>
      If the private key is lost or corrupted, all encrypted JDBC credentials stored in `jdbc_connections` will be unrecoverable. Back up `conf/dbimport_private_key.pem` to a secure location.
    </Warning>

  </Step>

  <Step title="Create the Configuration Schema">

    With the configuration file saved and the MySQL database and user created, run the setup tool to build the schema.

    ```bash
    bin/setup --createDB
    ```

    This command creates all required tables, views, and default rows in the MySQL configuration database. It is safe to run on an already-initialised database — it will not destroy existing data.

  </Step>

  <Step title="Create Hive Staging Databases">

    DBImport writes to intermediate staging tables in Hive during imports and exports. The staging databases must exist before any import or export is run.

    ```sql
    CREATE DATABASE etl_import_staging;
    CREATE DATABASE etl_export_staging;
    ```

    If you have changed `import_staging_database` or `export_staging_database` in the `configuration` table, use those names instead of the defaults above.

    ### Optional: create the Hive validation table

    If `hive_validate_before_execution` is set to `1` in the `configuration` table, DBImport runs a test query against a small Hive table before every execution to confirm Hive is responsive. Create that table now.

    ```sql
    CREATE DATABASE IF NOT EXISTS dbimport;

    CREATE TABLE dbimport.validate_table (id INTEGER, value STRING);

    INSERT INTO dbimport.validate_table (id, value)
    VALUES (1, 'Hive'), (2, 'LLAP'), (3, 'is'), (4, 'working'), (5, 'fine');
    ```

  </Step>

  <Step title="Update JDBC Driver Paths">

    DBImport ships with driver metadata for every supported database type, but it cannot bundle the actual JAR files due to licensing restrictions. Open the `jdbc_connections_drivers` table in your SQL client and update the `classpath` column for each database type you intend to use.

    The `classpath` value for a fresh installation reads `add path to JAR file`. Replace each placeholder with the full filesystem path to the correct JDBC JAR on the DBImport host. Also ensure that Sqoop's classpath includes the same JAR files.

  </Step>

</Steps>

## Spark Configuration

Spark settings are defined under the `[Spark]` section of `dbimport.cfg`. The correct values depend on your cluster distribution and Spark version. Verified configurations for each supported platform are shown below.

<Note>
  If you see the error **`SyntaxError: Missing parentheses in call to 'print'. Did you mean print(rack)?`** when DBImport submits a Spark job, your cluster's topology script is still running under Python 2. See the workaround below.
</Note>

<Accordion title="Fix: Python 2 topology script error">

The YARN topology script runs under Python 2 on some clusters. Sqoop and Spark both execute it, and Python 3 syntax in the main script can collide.

1. In `core-site.xml`, change `net.topology.script.file.name` to point to a new file, for example `/etc/hadoop/conf/custom_topology_script.py`.
2. Copy the original: `cp /etc/hadoop/conf/topology_script.py /etc/hadoop/conf/custom_topology_script.py`
3. Edit the first line of the new file from `#!/usr/bin/env python` to `#!/usr/bin/python2`.
4. Propagate the change to every node in the cluster.
5. Restart HDFS, YARN, and any other affected services.

</Accordion>

## Iceberg Support (Tech Preview)

<Note>
  Iceberg support is in tech-preview state and has not been used as extensively in stable production environments as standard imports. Keep this in mind before enabling it for critical workloads.
</Note>

CDP Private Cloud Base Edition does not include Iceberg support out of the box. To enable it, download the Iceberg Spark runtime JAR from the [Apache Iceberg release page](https://iceberg.apache.org/releases/) and copy it to all nodes in the cluster.

The version verified with CDP 7.1.8 is `iceberg-spark-runtime-3.3_2.12-1.1.0.jar`.

Add the JAR to the `jar_files` line in `[Spark]` alongside the HWC connector.

```ini
[Spark]
spark_major_version = 3
path_append         = /opt/cloudera/parcels/SPARK3/lib/spark3/python, /opt/cloudera/parcels/SPARK3/lib/spark3/python/lib/py4j-0.10.9.5-src.zip, /opt/cloudera/parcels/SPARK3/lib/hwc_for_spark3/pyspark_hwc-spark3-1.0.0.3.3.7180.5-1.zip
jar_files           = /opt/cloudera/parcels/SPARK3/lib/hwc_for_spark3/hive-warehouse-connector-spark3-assembly-1.0.0.3.3.7180.5-1.jar, /opt/datalake/jars/iceberg-spark-runtime-3.3_2.12-1.1.0.jar
py_files            = /opt/cloudera/parcels/SPARK3/lib/hwc_for_spark3/pyspark_hwc-spark3-1.0.0.3.3.7180.5-1.zip
master              = yarn
deployMode          = client
yarnqueue           = default
dynamic_allocation  = true
executor_memory     = 2688M
hdp_version         = 7.1.8.11-3
hive_library        = HiveWarehouseSession
```

The following HiveServer2 settings must also be enabled in CDP for Iceberg to function, even if you only access Iceberg tables through Impala or Spark.

| HiveServer2 setting | Required value |
|---|---|
| `hive.vectorized.execution.enabled` | `false` |
| `iceberg.engine.hive.enabled` | `true` |
| `tez.mrreader.config.update.properties` | `hive.io.file.readcolumn.names,hive.io.file.readcolumn.ids` |

<Note>
  Due to the TEZ-4248 limitation in CDP Private Cloud Base Edition, Iceberg tables created by DBImport cannot currently be accessed through Hive. Impala and direct Spark access work correctly.
</Note>

## Apache Atlas Integration

DBImport can publish data lineage information to Apache Atlas (version 1.1.0 or higher).

### 1 — Configure the Atlas address

In `dbimport.cfg`, set the Atlas server address and authentication method.

```ini
[Atlas]
address             = https://atlas.example.internal:21443
timeout             = 5
ssl_verify          = true
ssl_cert_path       = /etc/ssl/certs/ca-bundle.crt
authentication_type = kerberos
```

### 2 — Register the DBImport schema in Atlas

Run the following command from a session with a valid Kerberos ticket that has admin permissions in Atlas.

```bash
curl --negotiate -u : -i \
  -X POST \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  "https://<ATLAS_HOST>:<PORT>/api/atlas/v2/types/typedefs" \
  -d "@/usr/local/dbimport/atlas/dbimportProcess.json"
```

### 3 — Copy the DBImport lineage icon

Copy the DBImport process icon into the Atlas entity icon directory so that the lineage graph renders the correct logo.

<Tabs>
  <Tab title="HDP">
    ```bash
    cp /usr/local/dbimport/atlas/DBImport_Process.png \
       /usr/hdp/current/atlas-server/server/webapp/atlas/img/entity-icon/
    ```
  </Tab>
  <Tab title="CDP / CDH">
    ```bash
    cp /usr/local/dbimport/atlas/DBImport_Process.png \
       /opt/cloudera/parcels/CDH/lib/atlas/server/webapp/atlas/img/entity-icon/
    ```
  </Tab>

## Upgrading an Existing Installation

To upgrade DBImport, replace all binary files with the new version and then run the schema upgrade command. The upgrade command is idempotent — it applies only migrations that have not been applied yet and is safe to run even when the schema is already current.

```bash
./setup --upgradeDB
```

After upgrading, compare your local `conf/dbimport.cfg` against the distribution template `conf/dbimport.cfg.dist`. New versions may introduce configuration keys that DBImport will fail to start without. Add any missing keys from the template to your local configuration file.

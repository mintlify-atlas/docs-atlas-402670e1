DBImport has a specific set of prerequisites on both the server where it is installed and the Hadoop environment in which it operates. Review every item on this page before beginning the installation to avoid configuration problems later.

## Python

DBImport is verified with **Python 3.6** and **Python 3.8**. Other versions may work but are not tested. The Python version you choose also constrains the Spark version available to you.

<Note>
  Python 3.8 requires Spark 3. Running Python 3.8 with Spark 2 will cause errors during the ETL and Hive processing steps.
</Note>

It is strongly recommended to run DBImport inside a Python virtual environment to isolate its dependencies from other tools installed on the same host.

## Hive

DBImport connects to HiveServer2 using the **binary transport mode**. HTTP transport is not supported. An **LLAP** (Live Long and Process) instance is preferred over a standard HiveServer2 because of the significantly lower query startup latency it provides for the many short SQL statements DBImport issues during schema detection and ETL.

<Note>
  DBImport does not use the Hive JDBC driver for its internal ETL queries. It communicates with Hive through PyHive over the Thrift binary protocol. Ensure that port 10000 (or whichever port your HiveServer2 binary endpoint listens on) is accessible from the DBImport host.
</Note>

## Kerberos

**Kerberos is required.** DBImport does not support Hive clusters without Kerberos authentication. A valid keytab file and principal must be present on the DBImport host and configured in `dbimport.cfg` before any import can run. DBImport refreshes its Kerberos ticket automatically at the start of each execution.

## MySQL / MariaDB Configuration Database

DBImport stores all import definitions, connection strings, column overrides, Airflow DAG mappings, and statistics in a **MySQL or MariaDB** database.

<Note>
  MariaDB version **10.2.8 and earlier in the 10.2 series** are not supported due to an incompatibility with SQLAlchemy. Use either the **10.1.x** branch or **10.2.9 or newer**.
</Note>

The DBImport application user needs `CREATE TABLE`, `ALTER TABLE`, `INSERT`, `UPDATE`, `DELETE`, and `SELECT` permissions on the configuration schema so that `./setup --createDB` and `./setup --upgradeDB` can manage the schema automatically.

## Hive Metastore Database Access

DBImport requires a **direct JDBC connection to the Hive Metastore database** (the underlying SQL database that backs the Hive catalog — typically MySQL or PostgreSQL). This connection is used to read partition metadata, detect schema changes, and manage table definitions without going through HiveServer2 for every operation.

Configure the connection string in `dbimport.cfg` under `[Metastore]` → `hive_metastore_alchemy_conn` using a SQLAlchemy connection URL.

<Note>
  If `hive_remove_locks_by_force` is set to `1` in the `configuration` table, the Metastore database user must have `DELETE` permission on the `HIVE_LOCKS` table. Otherwise, read-only (`SELECT`) access is sufficient.
</Note>

## Sqoop and Spark

| Engine | Supported versions |
|---|---|
| Sqoop | Sqoop 1.x (on HDP or CDH/CDP) |
| Spark 2 | Works with Python 3.6 |
| Spark 3 | Required for Python 3.8; available as a separate parcel on CDP |

Sqoop cannot export data from Hive 3.x transactional tables. If your cluster runs Hive 3.x, you must use Spark for all exports.

## Hardware and Network

DBImport itself is a lightweight coordinator process — it issues SQL and spawns Sqoop/Spark jobs rather than processing data itself. The following considerations apply to the host running DBImport.

- **Network:** The DBImport host must have TCP access to the source JDBC database, HiveServer2 (binary, typically port 10000), the Hive Metastore database, and the MySQL configuration database.
- **Storage:** No large local storage is required. Sqoop and Spark write directly to HDFS or S3.
- **CPU / Memory:** A single-core, 2 GB node is sufficient for running the DBImport coordinator process itself. Spark executor resources are configured separately in `dbimport.cfg` and allocated from the YARN cluster.
